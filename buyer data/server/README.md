# 서버의 고객별 메모리와 주문 기록

현재 로컬 검색 앱은 로그인 없이 고정 소유자 `local-owner`로 동작한다. [서버 저장 코드](../../api_data/buyer_server.py)는 SQLite의 모든 조회, 저장, 삭제에 `buyer_id`를 적용한다. 서버 프로세스가 사용하는 DB의 기본 위치는 `~/.local/share/fcc-server/buyers.sqlite3`이며 `FCC_BUYER_DB_DIR`로 디렉터리를 지정할 수 있다.

| 레코드 | 저장할 값 | 수명 |
| --- | --- | --- |
| 고객별 메모리 `preference` | 구매자 ID, 선호 항목, 값과 단위, 저장을 선택한 시각, 수정 시각 | ‘다음에도 사용’으로 저장한 값만 본인 계정에서 재사용한다. 항목을 삭제하면 이후 추천에도 적용하지 않는다. |
| 상품 피드백 `feedback` | 구매자 ID, 판매처 상품을 식별하는 해시, 선택한 평가, 수정 시각 | 본인이 다시 평가하면 이전 값을 교체하고 삭제하면 해당 상품의 원래 정렬을 사용한다. |
| 이번 구매 요청 (설계) `purchase_request` | 구매자 ID, 요청 ID, 상품과 옵션, 수량, 이번 예산과 수령 기한 | 견적용 임시 입력은 취소 또는 만료 시 정리한다. 주문을 확정하면 선택한 조건을 해당 주문에 기록한다. |
| 주문 견적 및 결제 시도 (설계) `quote`, `payment_attempt` | 구매자와 주문 ID, 선택한 옵션, 견적 버전과 만료 시각, 금액과 통화, 승인 범위, 시도 ID, 판매처 거래 참조 및 확인 상태 | 주문 대조와 취소, 환불을 위한 기록으로 보관한다. 주문 기록의 보관 기간은 운영 전에 정한다. |

선호 항목은 MVP에서 신발 사이즈와 단위, 선호 통화, 배송 우선순위처럼 이름과 형식이 정해진 값으로 받는다. 대화 전문이나 주소를 자유 메모로 저장하지 않는다. 선호를 저장하거나 수정해도 결제 실행에는 해당 주문의 유효한 승인이 따로 필요하다.

## 고객 간 분리

- 선호의 고유 키는 `(buyer_id, preference_key)`로 둔다. 읽기, 쓰기, 삭제 시 현재는 서버가 개인용 ID를 정한다. 로그인 도입 시에는 검증된 발급자와 사용자 식별자로 결정한다. 주문과 견적을 열 때도 같은 소유자 조건을 적용한다.
- 향후 다중 사용자 모드에서는 로그인 전까지 세션 입력만 사용한다. 로그아웃이나 계정 변경 시 세션에 남은 선호, 견적, 검색 결과를 비운다. 고객별 조회 결과는 공용 캐시에 넣지 않는다.
- 공용 캐시에는 공개 카탈로그와 시세만 둔다. 어느 고객이 무엇을 조회하거나 선택했는지, 고객별 할인, 배송지에 따른 견적은 공용 값에 섞지 않는다.


## 검색 화면에서 사용

프로젝트 루트에서 [검색 화면](../../api_data/README.md#글과-음성으로-상품-검색)을 실행한다. 왼쪽 **내 구매 선호**에서 항목별로 저장하거나 삭제한다. 선호 통화는 고객 메모리이며 검색 가격은 기존대로 판매처 통화를 사용한다.

검색 결과 아래 **검색 결과 피드백**에서 상품과 평가를 선택한다. ‘찾던 상품’은 같은 결과 그룹 안에서 먼저 표시하고 ‘다른 상품’은 뒤에 표시한다. ‘배송 정보 부족’은 의견으로 저장하며 배송 확인 상태는 판매처 응답을 따른다. 서버에는 자유 입력이나 검색어 원문을 피드백으로 기록하지 않는다.

기본 설정은 `127.0.0.1`에서 실행한다. 개인용 앱을 터널이나 역방향 프록시로 다른 사람에게 공유하면 같은 소유자의 기록을 보게 된다. 외부 인터페이스에 직접 바인딩하면 앱은 공용 검색만 제공한다. 향후 로그인을 위한 `streamlit[auth]` 의존성은 준비돼 있다. 인증 공급자 설정과 기존 개인 기록을 본인 계정에 연결하는 작업은 로그인 도입 시 진행한다.
