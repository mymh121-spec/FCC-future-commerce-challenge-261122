# FCC (Future Commerce Challenge) 261122

이 문서는 사용자가 정한 범위 안에서 상품과 결제 경로를 고르는 구매 에이전트의 구현 설계다. 자연어 처리기는 요청을 구조화하고 결과를 설명한다. 서버는 재고·배송 기한·금액·권한을 검사하고 주문 상태를 변경한다. 입력 필드와 테스트 데이터는 [데이터 설계](DATA_SOURCES.md)에 정리했다.

개발과 테스트를 위해 직접 만들거나 코드로 생성한 임시 데이터는 [pp_data 폴더](./pp_data/)에 보관한다.

상품명이나 모델명을 직접 입력하거나 한국어로 말해서 검색할 수 있다. [로컬 상품 검색 실행 방법](api_data/README.md#글과-음성으로-상품-검색)

고객 기기의 암호화 파일과 서버에 보관할 계정별 선호, 주문별 기록은 [구매자 데이터 보관 기준](./buyer%20data/README.md)에서 확인할 수 있다.

## 구매 요청과 결제 권한

“생수 두 묶음을 금요일까지 2만 원 안에서 사줘”라는 요청에서 상품 규격, 수량, 예산, 수령 기한을 추출한다. 한 묶음에 몇 병인지에 따라 후보가 달라지면 규격을 확인한다. 상대 날짜는 사용자 시간대로 해석해 확정된 기한을 저장한다.

- **구매 요청**에는 이번 주문의 조건과 직접 선택 여부를 기록한다.
- **선호**에는 가격·배송 우선순위, 포인트 보존 여부 등 다음 구매에도 사용자가 재사용하겠다고 한 기준을 저장한다. 구매 이력에서 추론한 값은 추천에만 쓴다.
- **구매 승인**에는 사용자, 실행 주체, 허용 상품·대체 옵션·수량, 배송 기한, 결제수단, 원화·포인트 한도, 만료 시각과 사용 가능 횟수를 기록한다. 반복 구매는 승인 버전과 회차를 함께 식별한다.

“이번에는 다른 걸로”라는 요청을 받으면 해당 회차의 자동 실행을 보류하고 후보를 보여준다. 일회성 변경은 해당 주문에만 적용한다.

## 후보를 만들고 비용을 계산하는 순서

1. 판매처별 상품을 규격·묶음 수·옵션 단위로 맞춘다. 요청 수량을 충족하는 재고와 배송 기한을 검사하고, 허용된 대체품은 대체한 조건을 기록한다.
2. 상품 합계와 배송비에서 시작해 장바구니별로 사용 가능한 결제수단과 쿠폰 조합을 만든다. 적용 대상, 최소 구매액, 할인 한도, 유효기간, 중복 여부를 각 쿠폰의 적용 순서에 맞춰 검사한다. 범용 쿠폰과 더 큰 결제 할인이 양립할 수 없으면 두 조합을 따로 계산한다.
3. 각 조합에서 **지금 낼 금액**, **사용할 보유 포인트**, **나중에 받을 적립**을 따로 구한다. 포인트 차감 후 남은 금액을 허용된 결제수단으로 낼 수 있는지도 검사한다. 미래 적립과 청구 시점 할인은 현재 지출 한도에서 빼지 않는다.
4. 승인 조건을 충족하는 후보만 사용자 선호 순서로 정렬한다. 선호가 비어 있고 선택 결과가 달라지면 필요한 결정만 묻는다. 결과에 선택 이유와 탈락 사유를 함께 남긴다.

배송비 포함 50,000원에 공통 쿠폰 2,000원을 적용한 **가상 견적**은 다음과 같다.

| 결제 경로 | 지금 낼 금액 | 사용 포인트 |
| --- | ---: | ---: |
| 추가 쿠폰 3,000원 적용 | 45,000원 | 0P |
| 보유 포인트 사용 후 잔액 결제 | 42,000원 | 6,000P |
| 일반 카드 결제 | 48,000원 | 0P |

두 번째 경로는 현금 지출을 3,000원 줄이는 데 보유 포인트 6,000P가 든다. 포인트를 보존할 때는 첫 번째 경로를, 6,000P 사용을 승인하고 현금 지출 최소화를 원할 때는 두 번째 경로를 선택한다.

## 해외 견적

외화 상품가·국제 배송비·세금·전송 또는 결제 수수료를 통화별로 기록한다. 외화 합계에 포함된 세금을 원화 별도 납부액에 다시 더하지 않는다. 카드 환산에는 환율 출처, 기준 시각, 적용 수수료, 반올림 규칙을 남긴다. 확정액을 구할 수 없으면 비교 화면에 추정치로 표시한다. 디지털 자산 결제를 허용한 경우 보유분의 원화 가치, 부족분 충전 비용, 전송 비용을 합산한다. 원화 지출 상한을 확인할 수 있는 경로만 자동 실행 후보에 넣는다.

## 주문 상태와 결제 실행

| 시점 | 서버 동작 |
| --- | --- |
| 비교 완료 | 직접 선택 주문은 선택을 기다린다. 유효한 위임이 있는 주문은 승인 조건을 만족하는 후보를 재검증한다. |
| 조건 변경 필요 | 변경 전후 값을 제시한다. 예를 들어 “금요일까지 받으려면 이번 주문 한도를 2,000원 올릴까요?”라고 묻는다. 답변을 주문 ID와 승인 버전에 연결한 뒤 새 견적을 구한다. |
| 결제 직전 | 최신 견적·재고·배송일·포인트와 승인 버전·취소 여부를 다시 검사한다. 동일 주문 또는 반복 회차의 실행을 한 번만 확보하도록 DB에 유일성 제약을 둔다. |
| 결제 요청 | 주문에 결제 시도 ID와 멱등성 키를 먼저 저장한다. 같은 시도를 재전송할 때 같은 키를 사용한다. 추가 인증이 필요하면 사용자에게 넘긴다. |
| 응답 지연 | 상태를 ‘결과 확인 중’으로 두고 거래 조회 또는 검증된 결제 알림으로 결과를 대조한다. 성공이 확인되면 주문을 확정한다. 중복 알림은 같은 이벤트 ID로 걸러낸다. |
| 결제 후 주문 생성 실패 | 기존 거래를 식별해 주문을 복구하거나 취소·환불을 요청한다. 실제 처리 결과가 도착하면 최종 상태를 기록한다. |

반복 구매 해제와 결제 시작은 같은 승인 버전에 대한 조건부 갱신으로 순서를 정한다. 해제가 먼저 반영되면 새 결제 시도를 중단한다. 이미 전송된 요청은 거래 결과를 확인한 뒤 취소 가능 여부를 판단한다.

## 첫 구현과 검증

가격 계산과 후보 정렬은 같은 입력에 항상 같은 결과를 반환하는 함수로 작성한다. 재고 조회, 견적 갱신, 결제 요청, 거래 조회는 외부 입출력을 담당하는 코드로 분리한다. 그러면 로컬 모의 상점의 값을 바꾸는 것만으로 다음 동작을 확인할 수 있다.

- 포인트 정책을 바꾸면 위 표에서 고르는 경로가 달라진다.
- 배송이 늦거나 승인 한도를 넘는 최저가 후보는 제외된다.
- 견적 후 쿠폰이 만료되면 다른 유효 후보를 다시 찾고, 없으면 필요한 변경만 묻는다.
- 반복 승인이 해제된 대기 주문은 실행되지 않는다.
- 결제 응답 유실 후 성공 알림이 두 번 와도 주문은 한 번만 확정된다.
