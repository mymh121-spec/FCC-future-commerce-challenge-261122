# FCC (Future Commerce Challenge) 261122

사용자가 정한 조건 안에서 AI가 판매처·혜택·결제 수단을 비교하고 구매를 실행하는 커머스 프로젝트.

기준일: 2026-11-22 (KST)

기획 원문: [커미셜 후반 — Track A 발표 최종본](https://app.notion.com/p/420a9c24480e81d1b54ae2bc9e750cd0)

현재 단계는 구현 전 로직 설계다. 실제 결제 코드, 운영 배포, 파트너 API 연동은 아직 구현하거나 검증하지 않았다. 아래 데이터 구조, 함수 이름, 상태 전이 및 정책은 원문을 코드로 옮기기 위한 제안이다. 원문의 파트너 역할 역시 연동 구상이며, 사용 가능한 API나 계약이 확인되었다는 뜻이 아니다.

## 1. 서비스가 해야 하는 일

사용자가 “생수 두 묶음을 금요일까지 2만 원 안에서 사줘”라고 말하면, 서버는 상품 조건, 수량, 예산, 수령 기한, 허용 결제수단을 구조화한다. 상품명만으로 규격을 특정할 수 없으면 용량과 수량처럼 구매 결과를 바꾸는 조건부터 확인한다. 그다음 판매처별 재고와 배송일을 모으고, 적용할 수 있는 쿠폰과 결제 혜택을 계산해 승인 범위 안에 있는 후보를 찾는다.

AI는 자연어 해석과 결과 설명을 맡는다. 금액 계산, 권한 확인, 후보 제외, 결제 실행 여부는 서버의 명시적인 규칙으로 결정한다. AI가 작성한 문장이나 외부 상품 설명을 승인 증거로 사용하지 않는다.

수수료를 배분하는 커미션 정산 기능은 원문에 정의되어 있지 않다. 이 문서는 원문에 제시된 커머스 구매 흐름을 대상으로 한다.

## 2. 요청·선호·결제 권한을 따로 저장한다

`PurchaseRequest`에는 이번 구매의 상품, 옵션, 수량, 수령 기한, 예산과 구매 방식을 저장한다. 구매 방식은 후보를 보고 직접 고르는 `REVIEW`와 승인한 조건 안에서 맡기는 `DELEGATED`로 구분한다.

`Preference`에는 가격과 배송 중 무엇을 우선하는지, 브랜드를 바꿔도 되는지, 포인트를 얼마나 쓸지 같은 선호를 저장한다. “이번에는”이라는 답은 현재 요청에만 적용한다. “다음에도”라는 명시적인 의사가 있을 때만 재사용 가능한 선호로 저장한다. 구매 이력에서 추론한 선호는 추천에만 사용하며 결제 권한을 만들지 않는다.

`PurchaseMandate`에는 실제 승인 내용을 저장한다. 사용자와 실행 에이전트, 대상 상품 및 허용 대체 범위, 수량, 배송 기한, 결제수단, 건별 원화 한도, 포인트 사용 한도, 유효기간, 사용 횟수, 취소 여부와 버전을 포함한다. 반복 구매에는 구매 주기와 실행 회차 식별자도 필요하다. 선호를 바꿨다는 이유로 기존 승인 범위를 자동 확대하지 않는다.

“이번엔 다른 걸로”라는 요청은 이번 회차를 `REVIEW`로 전환하고 진행 중인 자동 실행을 보류한다. 새 상품이라도 이번 한 건의 조건을 승인하면 `DELEGATED`로 처리할 수 있다.

## 3. 판매처의 서로 다른 데이터를 같은 형태로 바꾼다

각 판매처 어댑터는 상품과 옵션 식별자, 규격, 판매 수량, 재고, 상품가, 배송비, 통화, 예상 도착일, 견적 시각 및 만료 시각을 `Offer`로 반환한다. 제품명이 비슷하다는 이유만으로 같은 상품으로 취급하지 않는다. 동일 상품·옵션 비교와 허용된 대체품 비교를 구분한다.

`collectOffers()`로 후보를 모으고 `filterEligibleOffers()`에서 재고, 수량, 배송 기한, 허용 브랜드·원산지·옵션 조건을 검사한다. 배송일이나 재고가 확인되지 않은 후보는 확인된 후보처럼 자동구매 대상으로 사용하지 않는다. 조회 오류는 품절이나 후보 없음과 별도로 기록한다.

## 4. 국내 가격은 실제 사용 가능한 혜택 조합으로 계산한다

우선 상품 합계에 배송비를 더한다. 현재 장바구니에서 함께 쓸 수 있는 범용 쿠폰을 적용한 비교 기준가를 만들고, PAYCO·OK캐쉬백·카드 직접 결제의 가능한 경로를 생성한다. 쿠폰은 최소 구매액, 대상 상품, 가맹점, 결제수단, 유효기간, 최대 할인액, 적용 순서와 중복 가능 여부를 모두 검사한다.

범용 쿠폰을 무조건 확정한 뒤 나머지 혜택을 더하면 더 저렴한 배타적 조합을 놓칠 수 있다. 따라서 `enumerateBenefitCombinations()`가 범용 쿠폰을 포함하는 조합과, 해당 쿠폰과 중복할 수 없는 다른 유효 조합도 열거하고 최종 결제액을 비교한다. 확인되지 않은 혜택과 중복 할인은 계산에 넣지 않는다.

각 경로는 `cashDueKrw`(지금 낼 원화), `pointsUsed`(사용할 보유 포인트), `futureReward`(나중에 받을 적립), 할인 내역과 비용 근거를 따로 반환한다. 포인트 적용 후 최소 카드 결제액, 사용 단위, 잔액과 사용 한도도 검사한다. 현금은 원 단위 정수로, 외화·환율 계산은 고정 정밀도 Decimal로 처리하고 반올림 시점을 정한다.

원문의 가상 예시에서는 배송비 포함 50,000원에 범용 쿠폰 2,000원을 적용한다.

| 경로 | 지금 낼 원화 | 사용하는 포인트 |
| --- | ---: | ---: |
| PAYCO 추가 쿠폰 | 45,000원 | 0P |
| OK캐쉬백 일부 사용 + 카드 | 42,000원 | 6,000P |
| 카드 직접 결제 | 48,000원 | 0P |

42,000원이 가장 낮다고 무조건 OK캐쉬백을 선택하지 않는다. 포인트 보존이 사용자 설정이면 PAYCO를 고르고, 포인트 사용을 허용하면서 현금 지출 최소화를 우선하면 OK캐쉬백 경로를 선택한다. 이를 위한 `KEEP_POINTS`, `MINIMIZE_CASH_WITHIN_POINT_LIMIT` 같은 정책 이름은 구현 제안이다. 포인트 정책에 따라 선택이 달라지는데 저장된 기준이 없으면 그 선택만 묻는다. 포인트의 원화 가치를 총비용 비교에 사용할 경우에는 확인된 전환 가치를 적용하고, 포인트를 공짜 할인으로 취급하지 않는다.

## 5. 해외는 추정 비용과 승인 가능한 비용을 구분한다

해외 카드 후보는 상품가, 국제 배송비, 예상 세금, 환율, 카드·해외 결제 수수료와 원화로 별도 납부할 비용을 구분해 계산한다. 이미 외화 결제액에 포함된 비용을 원화 비용에 다시 더하지 않도록 비용 항목마다 포함 여부를 기록한다. 확인할 수 없는 카드 혜택은 차감하지 않는다.

원문의 달러 주문 비교식은 `달러 결제액 × 매매기준율 × 1.025 + 원화 별도 납부 비용`이다. 이 2.5%는 비교용 가정이며 실제 청구 상한이 아니다. 환율의 출처와 시점, 추정 세금, 비용 불확실성도 함께 보관한다. 다른 통화에 이 가정을 근거 없이 확대하지 않는다.

USDC는 판매처 지원과 사용자의 허용을 모두 확인한 경우에만 후보로 만든다. 사용할 보유 잔액의 원화 환산 가치와 부족분 충전 비용을 중복 없이 계산하고, 전송·결제 비용을 더한다. 기존 잔액을 쓴다고 비용을 0원으로 기록하지 않는다. 실제 지갑 연결과 서명은 연동 범위가 확정된 뒤 구현한다.

추정액이 한도 안이라는 이유만으로 결제를 허용하지 않는다. 최종 원화 금액 또는 보수적인 최대 지출을 검증·통제할 수 있어야 자동 실행한다. 실제 상한을 보장할 수 없는 경로는 확인 필요 상태로 두며, 사용자의 단순한 추정액 승인만으로 상한 보장을 주장하지 않는다.

## 6. 필수 조건을 먼저 검사하고 남은 후보를 정렬한다

`validateHardConstraints()`는 상품·옵션·수량, 재고, 기한, 허용 결제수단, 포인트 한도, 지출 한도와 권한 유효성을 먼저 검사한다. 그다음 `rankCandidates()`가 사용자에게 승인된 우선순위로 정렬한다. 가격이 싸다는 이유로 배송 기한이나 원산지 제한을 무시하지 않는다.

원화 한도는 나중에 받을 캐시백을 빼기 전 지출액에 적용한다. 현금 지출에는 결제 시점 비용과 주문에 수반되는 원화 별도 납부 비용을 포함해 검증한다. 포인트 사용량은 별도의 승인 한도로 검증한다. 원문에 없는 통합 자산 한도가 필요하면 현금·포인트 가치·USDC 가치를 어떻게 합산할지 별도 정책으로 정의한다.

동점이면 포인트 보존, 더 이른 도착, 안정적인 식별자 순서처럼 일관된 기준을 사용한다. 최종 후보에는 선택 이유와 제외된 후보의 사유 코드를 붙인다. 사용자가 가격과 배송 중 어느 쪽을 선호하는지 몰라도 결과가 같다면 불필요하게 질문하지 않는다.

## 7. 승인 범위를 벗어나면 바뀌는 조건만 확인한다

조건을 지키는 후보가 없으면 `buildApprovalDelta()`가 가장 작은 변경안을 만든다. 예를 들어 “금요일까지 받으려면 2,000원이 더 필요합니다. 이번 주문 한도를 52,000원으로 바꿀까요?”처럼 기존 조건과 달라지는 부분을 보여준다. 후보 전체를 다시 고르게 할 필요는 없다.

사용자 응답은 주문 ID, 현재 승인 버전, 변경안 ID에 연결한다. 긍정 답변을 다른 주문이나 만료된 변경안의 승인으로 재사용하지 않는다. 승인되면 새 버전을 만들고 최신 견적부터 다시 검사한다. “이번만”이라는 승인은 반복 구매의 기본 한도를 바꾸지 않는다. 기한과 금액을 함께 바꿔야 한다면 한 제안 안에 변경되는 조건을 모두 명시한다.

“한 번만 묻는다”는 같은 조건을 반복 질문하지 않는 UX 원칙이다. 승인 후 추가로 조건이 바뀌거나 결제 인증이 필요한 경우까지 무조건 한 번의 질문으로 끝낸다는 뜻은 아니다.

## 8. 결제 직전에는 서버가 다시 검사한다

`executePurchase()`는 최신 재고·견적·혜택을 조회하고, 해당 주문의 최신 승인 버전과 취소 여부를 읽는다. 최신 견적과 승인 조건이 맞을 때만 서버가 검증한 결제 명령을 생성한다. 명령에는 주문·견적·승인 식별자, 버전, 결제 금액, 사용 포인트, 결제수단, 만료 시각과 멱등성 키를 묶는다. 승인 후 클라이언트가 금액이나 상품을 바꿔 끼울 수 없게 한다.

주문과 반복 구매 회차에 유일성 제약을 두고, 실행 잠금과 상태 전이를 원자적으로 처리한다. `idempotencyKey`는 동일 결제 시도의 재전송에서 유지한다. 결제 결과가 불명확한 상태에서 새 키로 다시 청구하지 않는다. 가능하다면 카드 승인 후 재고 확정과 매입 단계를 분리하되, 실제 PG가 제공하는 흐름에 맞춘다.

결제 요청 타임아웃은 실패가 아니라 `PAYMENT_UNKNOWN`으로 처리한다. 웹훅과 거래 조회로 먼저 결과를 확인한다. 웹훅은 서명과 이벤트 중복 여부를 검증한다. 결제 성공과 주문 생성의 부분 실패에는 취소·환불 또는 복구 절차를 적용하고, 외부 시스템에 대해 무조건적인 exactly-once 처리를 주장하지 않는다.

본인 확인이나 결제 인증이 추가로 필요하면 `AUTH_REQUIRED`로 전환한다. 인증이 필요 없다고 가정한 자동결제 코드를 작성하지 않는다.

## 9. 자동구매 해제는 실행 중인 작업에도 전달한다

“이 상품의 반복 자동구매를 꺼줘”라는 요청은 승인 상태를 `REVOKED`로 바꾸고 버전을 올린다. 예약 작업을 해제하며, 대기·견적·승인 대기 주문을 취소한다. 실행기는 외부 결제 요청을 보내기 직전까지 최신 권한을 검사한다.

권한 해제와 결제 시작이 동시에 발생하면 같은 승인 레코드에 대한 잠금 또는 조건부 갱신으로 순서를 결정한다. 이미 결제 요청이 전송된 주문은 즉시 취소됐다고 표시하지 않고 결과를 조회한 뒤 가능한 취소·환불 경로로 처리한다. 결제된 주문의 취소와 미래 구매 권한 해제는 서로 다른 작업이다.

## 10. 상태와 데이터 구조

일반 상태는 `DRAFT → QUOTING → AWAITING_APPROVAL 또는 READY → REVALIDATING → EXECUTING → PURCHASED`로 진행한다. 별도 분기로 `AUTH_REQUIRED`, `PAYMENT_UNKNOWN`, `FAILED`, `CANCELLED`, `REFUND_PENDING`, `REFUNDED`를 둔다. 견적 만료는 재조회로, 권한 만료·해제는 자동 실행 중단으로 연결한다. 결과가 불명확한 결제를 단순 실패로 바꾸지 않는다.

| 데이터 | 역할 |
| --- | --- |
| PurchaseRequest | 이번 구매 조건과 REVIEW/DELEGATED 방식 |
| Preference | 명시적으로 재사용을 허용한 선호와 적용 범위 |
| PurchaseMandate | 승인 조건, 버전, 유효기간, 사용 횟수, 해제 상태 |
| Offer / Quote | 판매처 후보, 비용 근거, 재고·배송, 조회 시각과 만료 |
| Benefit / PaymentRoute | 쿠폰 호환성, 포인트, 카드, 현금 지출과 미래 적립 |
| ApprovalDelta | 변경 제안과 해당 주문·승인 버전에 연결된 응답 |
| Order / PaymentAttempt | 주문 상태, 실행 회차, 멱등성 키, 거래 식별자 |
| AuditEvent | 어떤 승인과 견적으로 선택·제외·실행했는지 기록 |

카드번호와 인증 비밀은 일반 애플리케이션 DB나 로그에 저장하지 않고 결제 제공자의 토큰을 참조하는 설계를 사용한다. 주소 등 사용자별 자료 접근에는 소유자 검사를 적용한다. 감사 로그에는 승인과 비용 판단을 재현할 정보만 남기고 인증 비밀은 남기지 않는다.

## 11. 파트너 연결은 어댑터로 분리한다

원문에서 Minds는 메모리와 대화, AIR는 필요한 자격과 대리 권한 확인, NHN커머스는 국내 상품·장바구니, PAYCO와 OK캐쉬백은 결제 혜택·포인트, AP2는 승인 조건과 결제 요청 검증, Google Cloud는 실행 환경의 역할로 제안되었다. KSNET은 국내 PG 후보이며 USDC는 선택 가능한 해외 경로다.

핵심 로직에서 파트너 SDK를 직접 호출하기보다 `CatalogProvider`, `BenefitProvider`, `MemoryProvider`, `AuthorityVerifier`, `MandateVerifier`, `PaymentProvider` 인터페이스를 둔다. 파트너 계약, 실제 API, 테스트 계정, 인증 방식과 지원 범위를 확인하기 전에는 목 어댑터를 사용한다. 임의의 JSON 서명 구조를 AP2 준수 구현이나 AIR 연동 완료로 표시하지 않는다.

## 12. 구현 순서와 검증 시나리오

첫 구현은 국내 단일 상품 주문과 목 결제로 범위를 좁힌다. 원문의 세 경로를 재현하는 견적 데이터, 쿠폰 조합 계산, 포인트 정책에 따른 정렬, 승인 비교, 변경 질문, 결제 직전 재검증을 먼저 만든다. 화면과 AI 모델 연결은 이 결정 로직을 API로 호출하도록 붙인다. 이후 반복 구매·권한 해제, 해외 추정, 실제 파트너 샌드박스 순으로 확장한다.

추천 코드 구획은 `domain/`(요청·견적·승인), `pricing/`(쿠폰·포인트·외화 계산), `policy/`(필수 조건·정렬), `orchestration/`(상태 전이·재검증), `adapters/`(외부 연결), `api/`(사용자 입력과 승인), `tests/`(주요 시나리오)다. 언어·프레임워크는 아직 확정하지 않는다.

아래는 구현 후 통과시켜야 할 테스트 계획이며, 현재 테스트 통과를 의미하지 않는다.

- 포인트 보존이면 PAYCO 45,000원, 포인트 사용 허용·현금 최소화이면 42,000원 + 6,000P를 선택한다.
- 중복 불가 쿠폰, 최소 구매액 미달, 만료 쿠폰은 할인 계산에서 제외한다.
- 미래 캐시백을 차감해야만 한도 안에 들어오는 주문은 자동결제하지 않는다.
- 견적 이후 가격·재고·배송일이 바뀌면 최신 승인 조건으로 다시 판단한다.
- 일회성 승인과 이번 회차의 상품 변경은 반복 구매의 기본 선호와 권한을 확대하지 않는다.
- 중복 실행과 타임아웃 재시도로 결제가 중복 청구되지 않도록 거래 결과를 대조한다.
- 자동구매 해제와 실행이 겹쳐도 해제 이후 새 결제 요청을 시작하지 않도록 원자적 경계를 검증한다.
- 해외 2.5% 추정만으로 실제 원화 상한을 보장했다고 처리하지 않는다.
- 외부 연동 장애, 부분 결제, 주문 생성 실패와 환불 미완료를 성공으로 표시하지 않는다.

## 아직 결정해야 할 사항

실제 파트너 API와 이용 자격, 결제 권한 증빙 방식, 배송 보장 수준, 포인트의 사용자 정책, 반복 구매의 주기·횟수 제한, 해외 결제 상한 통제 방식, 취소·환불 책임 경계는 구현 전에 확정해야 한다. 서비스 자체 수수료나 판매자 커미션을 추가한다면 수취 주체, 산정 기준, 결제 전 고지, 취소 시 정산 규칙을 별도 요구사항으로 정의한다.
